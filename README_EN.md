# STM32 Keil Starter Project Generator

A local Windows desktop application that generates a minimal STM32 HAL Keil project from an installed STM32Cube SDK and Keil Device Family Pack (DFP). The project XML and linker scatter file are generated by the application; no Keil project template is required or bundled.

## Features

- Scans standard STM32Cube SDK layouts for recognized STM32 HAL families.
- Scans locally installed Keil DFPs and lists devices with the required device, SVD, and Flash algorithm files.
- Derives the device define, startup file, CPU core, and memory information from the SDK and DFP.
- Creates a starter project with CMSIS, HAL, user files, Keil project files, and output directories.
- Generates the Keil project configuration and linker scatter file, then validates referenced files.
- Optionally invokes the locally installed Keil uVision for a build.
- Creates a VS Code GBK encoding setting for Chinese source comments commonly used in Keil projects.
- Does not overwrite non-empty destination directories and cleans up temporary output after generation failures.

## Requirements

- Windows
- Python 3.10 or later (to run from source or build the application)
- The STM32Cube SDK and Keil DFP for the target device
- Keil MDK/uVision (only if you want to build the generated project)

The STM32Cube SDK, DFP, and Keil toolchain must be provided locally by the user. They are not included or redistributed by this project.

## Run from source

```powershell
python -m pip install -r requirements.txt
python main.py
```

## Build the Windows executable

```powershell
.\build_windows.ps1
```

The script creates a local virtual environment, installs the build dependencies, and produces `dist\STM32KeilProjectCreator.exe`.

## Usage

1. Select an extracted STM32Cube SDK root directory and scan it.
2. Select a detected MCU family and device.
3. Choose a new or empty destination directory and set the project name.
4. Generate the project. If Keil is installed locally, you can optionally invoke uVision after generation.

DFP roots are discovered from the Keil installation and common Packs locations. If a complete DFP is not installed, install the device pack with Keil Pack Installer and scan again.

## Generated project layout

```text
ProjectRoot/
├── Drivers/
│   ├── BSP/                         # Reserved for board support code
│   ├── SYSTEM/                      # Reserved for system-level code
│   └── Platform/
│       ├── CMSIS/
│       │   ├── Include/             # CMSIS core headers
│       │   └── Device/ST/<Family>/
│       │       ├── Include/         # Device and register headers
│       │       └── Source/Templates/ # system_<family>.c and startup file
│       └── <Family>_HAL_Driver/
│           ├── Inc/                 # HAL headers
│           └── Src/                 # HAL source files
├── Application/                     # Reserved for application code
├── Middlewares/                     # Reserved for middleware
├── Utilities/                       # Reserved for utility code
├── Users/
│   ├── main.c
│   ├── <family>_hal_conf.h
│   └── <family>_it.c
├── Project/
│   └── MDK-ARM/
│       └── <project>.uvprojx
├── Output/                          # Scatter file and build output
│   └── <project>.sct
├── .vscode/
│   └── settings.json                # GBK default source-file encoding
└── readme.txt
```

`BSP`, `SYSTEM`, `Application`, `Middlewares`, and `Utilities` are currently empty directories reserved for future additions; their presence does not mean that drivers or application implementations are generated. The Keil project uses the groups `Startup`, `User`, `Drivers/<Family>_HAL_Driver`, and `Readme`. These are project-view groups and do not necessarily map one-to-one to disk folders.

## Compatibility notes

Device discovery depends on the local SDK and DFP following layouts recognized by the application. The generator expects a standard STM32Cube HAL directory layout and a device with one contiguous Flash region and one main RAM region. Devices with multiple memory regions or non-standard layouts are rejected.

Being discoverable or project-generatable does not mean that a device has been tested with every board or clock configuration. Build with the matching local SDK/DFP, then verify the result on the target hardware.
